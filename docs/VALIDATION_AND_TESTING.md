# PoultryDetect — Validation and Performance Testing

## 1. Scope

This document separates three different kinds of evidence so that academic claims remain accurate:

1. **Independent project validation** of the earlier lightweight fallback classifier.
2. **Upstream-reported metrics** for the attributed MobileNetV2 transfer-learning checkpoint used by the live app.
3. **Production engineering tests** for build integrity, API behavior, authorization, model contract, deployment and runtime metadata.

No veterinary or clinical validation is claimed.

---

## 2. Independent Lightweight-Model Validation

Before MobileNetV2 was made the primary production model, the project trained a balanced multinomial logistic-regression image classifier using handcrafted image features.

Validation subset used in that experiment: **713 images**.

### Overall result

- Accuracy: **87.38%**

### Per-class result

| Class | Precision | Recall | F1 |
|---|---:|---:|---:|
| Coccidiosis | 0.935 | 0.935 | 0.935 |
| Healthy | 0.854 | 0.850 | 0.852 |
| Newcastle | 0.773 | 0.814 | 0.793 |
| Salmonella | 0.892 | 0.870 | 0.881 |

### Confusion matrix

Rows are actual classes and columns are predicted classes in the order:

```text
Coccidiosis, Healthy, Newcastle, Salmonella
```

```text
[[187,   0,  6,   7],
 [  3, 170, 16,  11],
 [  5,  13, 92,   3],
 [  5,  16,  5, 174]]
```

This experiment validates the **fallback classifier only**. It must not be quoted as MobileNetV2 performance.

## 3. MobileNetV2 Upstream-Reported Evaluation

The live MobileNetV2 checkpoint is an attributed MIT-licensed reference model converted to TensorFlow.js for PoultryDetect.

The upstream project reports:

| Metric | MobileNetV2 Transfer Learning |
|---|---:|
| Training loss | 0.06 |
| Validation loss | 0.32 |
| Training accuracy | 0.98 |
| Validation accuracy | 0.90 |
| Model size | 9.13 MB |
| Parameters | 2,263,108 |
| Input size | 128 × 128 × 3 |
| Test accuracy | 0.93 |
| Test F1 | 0.90 |

The upstream comparison table reports validation F1 = **0.88**, while its following prose states **0.84**. Because the source is internally inconsistent on that one value, PoultryDetect does not promote a single validation-F1 number as verified.

Source model and provenance are recorded in:

```text
client/public/models/mobilenetv2/PROVENANCE.txt
client/public/models/mobilenetv2/LICENSE-UPSTREAM.txt
```

These metrics are **not described as an independent PoultryDetect re-evaluation**.

## 4. Reproducible MobileNetV2 Evaluation

Evaluator:

```text
ml/evaluation/evaluate_mobilenet.py
```

Given the exact `.h5` checkpoint and a declared validation/test image directory, it generates:

- total sample count
- class counts
- accuracy
- macro precision / recall / F1
- weighted precision / recall / F1
- per-class precision / recall / F1
- confusion matrix JSON
- confusion matrix CSV

Example:

```bash
python ml/evaluation/evaluate_mobilenet.py \
  --model mobilenetv2.h5 \
  --split-dir organized_dataset/val \
  --output-dir ml/evaluation/results
```

A metric generated by this script may be labelled an **independent project evaluation** only when the exact dataset split is also recorded.

## 5. Production Model Contract Testing

GitHub Actions verifies the TensorFlow.js deployment artifact on every relevant change.

Contract checks:

- TensorFlow.js format is `layers-model`
- input shape is `[null, 128, 128, 3]`
- final Dense layer has 4 units
- final activation is Softmax
- all declared weight shards exist and are non-empty
- provenance file exists
- upstream license file exists

Workflow:

```text
.github/workflows/quality_checks.yml
```

This catches accidental replacement by an incompatible model before the application is considered build-valid.

## 6. Frontend Build and Delivery Performance

After TensorFlow.js was changed to dynamic import, the Vercel production build separated the normal app bundle from the ML runtime.

Observed production build output from that optimization stage:

| Asset | Approx. minified size | Approx. gzip size | Loading behavior |
|---|---:|---:|---|
| Main application JS | 460.39 KB | 135.34 KB | Initial application load |
| TensorFlow.js chunk | 1,915.89 KB | 305.90 KB | Lazy-loaded when a scan needs ML |
| App CSS | 52.88 KB | 11.83 KB | Initial application load |

The converted model payload consists of `model.json` plus three weight shards. The weight shards total roughly **8.6 MiB**, so keeping TensorFlow.js and model loading out of the initial application path is important for login/dashboard responsiveness.

The production `model.json` endpoint was checked successfully with HTTP status **200** after deployment.

## 7. Runtime Prediction Telemetry

Each prediction result records or can display:

```text
modelName
modelVersion
inferenceMs
usedFallback (runtime UI state)
```

This makes it possible to distinguish:

- `MobileNetV2 Transfer Learning` / TensorFlow.js primary inference
- `Lightweight Browser Classifier` fallback inference

Inference time is measured in the user's browser and therefore varies by device, browser, cached model state and hardware acceleration availability.

## 8. Express + MongoDB Security and CRUD Tests

The backend smoke test uses an isolated temporary MongoDB instance and verifies the core authenticated lifecycle and authorization boundaries:

1. `/api/health` returns a valid service response.
2. Unauthenticated history access is rejected with `401`.
3. Invalid registration input is rejected.
4. Registration creates a MongoDB user and JWT.
5. Duplicate registration is rejected.
6. Wrong-password login is rejected.
7. Login validates credentials and returns a JWT.
8. `/api/auth/me` verifies the authenticated session.
9. Invalid prediction-history payloads are rejected.
10. Authenticated history POST stores a prediction with model/context metadata.
11. History GET returns the authenticated user's record.
12. A second user cannot delete the first user's record.
13. The owner can delete the record.
14. A follow-up GET confirms deletion.

Command:

```bash
cd server
npm install
npm test
```

The CI test uses `mongodb-memory-server` so it is reproducible without modifying production data. The deployed production API separately uses MongoDB Atlas.

## 11. Security Controls Covered by the Audit

Current production/API hardening includes:

- bcrypt password hashes
- password field excluded from normal Mongoose queries
- HS256-pinned JWT signing/verification
- auth-specific rate limiting
- general API rate limiting
- Helmet response headers
- explicit production CORS allowlist
- JSON/body-size limits
- auth-field validation
- prediction/class/probability/symptom/environment validation
- authenticated user scoping for history operations
- Vercel browser security headers
- `.env` and build artifacts excluded via repository `.gitignore`

One remaining security-operational step is to rotate deployment secrets that were exposed during interactive setup before treating the project as frozen for final submission.

## 12. Interpretation Rules for Report and Viva

Safe statements:

- “The production application uses an attributed MobileNetV2 transfer-learning checkpoint through TensorFlow.js.”
- “The upstream project reports 90% validation accuracy and 93% test accuracy for the selected MobileNetV2 transfer-learning model.”
- “Our earlier independently tested fallback classifier achieved about 87.4% on the project validation subset.”
- “The live backend uses Node.js, Express, JWT and MongoDB Atlas.”
- “Automated tests verify authentication, history CRUD and cross-user isolation.”

Statements to avoid:

- “Our team trained the exact production MobileNetV2 checkpoint” — this is not true for the current reference checkpoint.
- “The model is 93% accurate on all farms” — upstream test accuracy does not establish field/general clinical accuracy.
- “The output is a veterinary diagnosis” — it is an academic screening result.
- “Every browser/device interaction has been fully automated and verified” — current evidence includes CI/API/deployment checks, not exhaustive browser automation.
